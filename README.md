# 1. 总体目标

完成作品集资料向网站项目的系统化迁移，网站美观，项目页面尊重作品集中每个项目的逻辑和阅读顺序。

本轮工作只聚焦以核心成果：

## 成果：将项目内容放入现有网站原型

1. 建立或完善建筑、景观和装置三个板块。
2. 每个板块具有项目列表页面。
3. 每个项目具有独立详情页面。
4. 将已导出的图片和已确认的文字放入项目页面。
5. 根据图片比例和项目叙事顺序，有限度调整现有原型。
6. 保持网站整体黑白视觉体系、导航逻辑和版式语言一致。
7. 不进行与内容迁移无关的大规模品牌设计、动画设计或技术栈重构。

# 4. 文件转换规则

## 4.1 InDesign

对于 INDD 或 IDML：

1. 优先使用本机 Adobe InDesign 及其脚本接口。
2. 打开文件前检查本地关联文件。
3. 自动修复仅限于能够在项目目录或其 Links 文件夹中明确找到的链接。
4. 不得用名称相似但无法确认的文件替代缺失链接。
5. 根据文档结构导出页面或跨页。
6. 优先导出高质量 PDF 或 PNG，再生成网页版本。
7. 提取文本框中的真实文字。
8. 保存文字与原始页码、文本框或文件的对应关系。
9. 如果缺失字体，仅允许使用文档可生成的现有预览或 PDF，不得永久替换源文件字体。
10. 如果无法可靠打开，标记为 blocked 并继续处理其他项目。

## 4.2 Photoshop

对于 PSD 或 PSB：

1. 优先使用本机 Adobe Photoshop 及其脚本接口。
2. 如果文件含有画板，分别导出有效画板。
3. 如果没有画板，导出可靠的合成预览。
4. 不得覆盖或扁平化源文件。
5. 尽可能提取可识别的文字图层。
6. 如果第三方工具无法正确还原图层效果，停止该文件转换并记录原因。
7. 不得用破损或明显错误的图片进入正式网站。

## 4.3 PDF、AI和普通图片

* PDF：按页面导出，保留页面顺序。
* AI或EPS：优先使用 Illustrator、PDF兼容数据或已有导出文件。
* JPG、PNG、TIFF：检查尺寸、方向、色彩和重复情况。
* DOCX、TXT、MD：提取文本，但不得自动改写原意。
* 视频或动画：本轮只记录和生成封面，不做复杂播放器开发。

## 4.4 导出质量

为网页生成的图片应：

* 保持原始宽高比；
* 不裁切重要设计内容；
* 不无意义放大低分辨率图片；
* 避免重复压缩；
* 保持图纸细线和文字可读；
* 为列表页生成缩略图；
* 为详情页生成较高分辨率版本；
* 优先沿用参考项目使用的图片格式；
* 如果参考项目没有明确标准，优先生成 WebP，同时保留可靠的高质量源导出。

图片名称使用稳定、可排序的序号，例如：

* `001-cover.webp`
* `002-context.webp`
* `003-site-plan.webp`
* `004-section.webp`

如果无法确认图片内容，使用：

* `001-image.webp`
* `002-image.webp`

不得编造图片描述。

# 5. 项目文字规则

只使用可以从以下来源确认的文字：

* InDesign 文本框；
* PSD 文字图层；
* DOCX、TXT或Markdown；
* PDF中的实际文字；
* 已存在的网站项目内容；
* 明确的文件名和项目标题。

项目文字可以整理格式，但不得擅自改写项目事实。

不得编造：

* 项目年份；
* 项目地点；
* 项目面积；
* 项目客户；
* 合作者；
* 获奖信息；
* 项目职责；
* 建成状态；
* 项目概念；
* 技术数据。

无法确认的字段应设置为：

* 空值；
* `null`；
* `TODO: verify`；
* `unknown`。

不得为了让页面看起来完整而生成虚假的项目介绍。

每段文字必须在 manifest 中记录其来源文件。

如果只能通过OCR提取文字：

1. 标记为低置信度；
2. 不直接作为最终正式文字；
3. 写入待核对字段；
4. 不得自动纠正专有名词和项目名称。

# 6. 网站内容结构

网站必须保持三级导航：

1. 首页；
2. Architecture、Landscape、Installation 项目列表；
3. 独立项目详情页。

优先沿用现有框架、路由、组件和数据结构。

不得无必要：

* 更换前端框架；
* 更换路由方案；
* 引入大型UI组件库；
* 引入CMS；
* 重写全部CSS；
* 改变现有构建工具；
* 删除已经工作的页面。

项目内容应尽可能数据驱动。

避免为每个项目复制一套完全独立的页面代码。

所有项目至少应有：

* slug；
* title；
* category；
* cover；
* image list；
* description或明确的待补充状态；
* source references；
* processing status。

# 7. 原型调整规则

当前原型是基本框架，不要求所有项目机械使用完全相同的图片布局。

允许根据项目内容采用有限的布局变化，例如：

* 单张全宽图片；
* 两张并排图片；
* 纵向长图；
* 横向全景图；
* 图纸网格；
* 文字加图片；
* 带说明的图片序列。

原型调整必须满足：

1. 保持黑白配色；
2. 保持统一字体层级；
3. 保持统一导航；
4. 保持统一页面宽度和间距逻辑；
5. 不加入与整体风格冲突的颜色和装饰；
6. 不为单个项目创造完全不同的网站语言；
7. 优先解决图片比例和可读性问题；
8. 不花费主要时间制作动画、过渡和视觉特效。

每次改变原型结构时，将原因记录在：

`docs/portfolio-import/RUN_LOG.md`

# 8. 项目处理顺序

按以下顺序处理：

1. 完整分析参考项目；
2. 选择一个未完成的小项目作为试点；
3. 完成试点项目的文件转换、文字提取和网页落位；
4. 构建并检查网站；
5. 确认流程有效后再批量处理；
6. Architecture；
7. Landscape；
8. Installation；
9. Unclassified；
10. 最终构建和总检查。

不要一开始同时修改所有项目。

一个项目失败时：

1. 最多进行两次有依据的修复尝试；
2. 仍失败则标记 blocked；
3. 记录阻碍；
4. 继续处理下一个项目。

不得因为单个损坏文件停止全部任务。

# 9. 持续工作与检查点

每完成一个项目，更新：

* `PROJECT_INVENTORY.csv`
* `ASSET_MANIFEST.json`
* `RUN_LOG.md`

每完成三个项目或一个主要阶段：

1. 运行网站构建；
2. 检查错误；
3. 保存当前工作状态；
4. 如果项目使用 Git，创建一个清晰的本地检查点提交；
5. 不得 force push；
6. 不得修改远程仓库历史。

RUN_LOG应记录：

* 已完成项目；
* 当前项目；
* 成功导出的文件；
* 提取的文字；
* 被阻止的文件；
* 网站构建状态；
* 下一步；
* 所有重要假设。

使用八小时作为最大工作预算，而不是完成标准。

在接近预算结束时，优先：

1. 保存所有已经完成的结果；
2. 更新清单和日志；
3. 确保网站处于可以构建或可明确恢复的状态；
4. 不要在最后阶段开始高风险重构；
5. 输出剩余任务清单。

# 10. 网站验证

每个项目完成后检查：

* 项目路由可以打开；
* 封面图片存在；
* 所有正式引用图片存在；
* 没有404资源；
* 图片顺序正确；
* 图片没有明显变形；
* 文字没有乱码；
* 中文和英文可以正常显示；
* 列表页可以进入详情页；
* 详情页可以返回分类页；
* 页面没有明显横向溢出。

全量完成后运行：

* build；
* lint；
* 已有测试；
* Playwright或等效浏览器检查。

至少检查以下尺寸：

* Desktop：1440 × 900；
* Tablet：768 × 1024；
* Mobile：390 × 844。

为主要页面输出截图。

将截图保存在：

* `figma-handoff/desktop/`
* `figma-handoff/tablet/`
* `figma-handoff/mobile/`

# 11. Figma交付目标

网页代码不能被默认视为已经转换成完全可编辑的Figma设计。

先检查当前环境是否具有可写入Figma的MCP、插件或其他工具。

如果具备可靠的Figma写入能力：

1. 创建首页桌面Frame；
2. 创建三个分类列表Frame；
3. 创建至少一个典型项目详情Frame；
4. 使用Auto Layout；
5. 建立基础文字样式；
6. 建立黑、白、灰变量；
7. 建立导航、项目卡片和图片模块组件；
8. 保持图层名称清晰；
9. 不覆盖已有Figma文件中的正式设计。

如果当前Figma工具只有读取能力，或没有Figma工具，则不要阻塞主要网站任务。

改为生成Figma handoff，包括：

* 桌面、平板和手机截图；
* `design-tokens.json`；
* `component-map.md`；
* `route-map.md`；
* 图片资产索引；
* 页面尺寸说明；
* 字体、间距和布局说明。

不得声称截图已经是可编辑的Figma图层。

# 12. 禁止事项

不得：

* 修改原始作品集文件；
* 删除无法识别的文件；
* 将私人项目文件上传到外部网站；
* 自动安装来源不明的软件；
* 绕过Adobe授权；
* 用低质量预览冒充成功导出；
* 编造项目文字；
* 擅自更换网站技术栈；
* 为了视觉完整而制造虚假项目；
* 隐藏失败文件；
* 将blocked项目标记为完成；
* 在没有验证的情况下宣布全部完成。

# 13. 阻碍处理

遇到以下情况时，将文件标记为 blocked：

* InDesign、Photoshop或Illustrator不可用；
* 软件要求人工登录或授权；
* 文件损坏；
* 缺少关键链接；
* 缺少字体导致无法可靠导出；
* 无法判断项目归属；
* 无法判断页面顺序；
* 文字来源不可靠；
* 文件需要人工设计决策；
* 当前权限无法读取文件。

将问题记录在：

`docs/portfolio-import/BLOCKED_FILES.md`

每条记录包括：

* 项目名称；
* 文件路径；
* 文件类型；
* 已尝试的方法；
* 错误信息；
* 未继续处理的原因；
* 需要用户执行的具体动作；
* 处理该问题后如何恢复工作。

除非整个任务都无法继续，否则记录后继续处理其他项目。

# 14. 完成标准

只有同时满足以下条件时，才能宣布本轮目标完成：

1. 所有发现的项目文件夹都出现在项目清单中。
2. 每个项目都有明确状态：

   * completed；
   * partial；
   * blocked；
   * unclassified。
3. 所有能够可靠转换的文件都已经完成转换。
4. 所有导出的图片都能追溯到原始文件。
5. 所有正式网站文字都有明确来源。
6. 建筑、景观和装置都有项目列表页面。
7. 已处理项目都有可访问的详情页。
8. 网站成功构建。
9. 主要路由经过浏览器检查。
10. Figma handoff已经生成。
11. blocked项目没有被隐藏。
12. 最终报告已经生成。

最终报告保存到：

`docs/portfolio-import/FINAL_REPORT.md`

最终报告必须包含：

* 发现的项目总数；
* 完成项目数；
* 部分完成项目数；
* blocked项目数；
* 导出图片总数；
* 提取文字总数；
* 网站页面总数；
* 运行过的测试；
* 构建结果；
* Figma交付情况；
* 原型发生的改变；
* 所有未解决问题；
* 下一次继续工作的准确起点。

在未达到以上标准时，不得使用“全部完成”或“任务完成”等表述。
